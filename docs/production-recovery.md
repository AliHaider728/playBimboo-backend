# Production incident and recovery: PlayBimboo

## Verified 13 October 2026

OPTIONS /api/categories with storefront Origin and content-type preflight returned HTTP 503, text/html, server LiteSpeed, and no Access-Control-Allow-Origin. GET /api/health returned the same HTML 503. These are not the JSON health errors generated by Express. The precise hosting failure requires Passenger/LiteSpeed logs; possible causes include startup dependencies, app mapping, worker/resource limits, or filesystem permissions.

Storefront / returned 200, x-nextjs-cache: STALE, and s-maxage=60 with a long stale-while-revalidate period. The reported CSS asset returned 200, text/css, and immutable cache headers. No proof of a missing CSS asset or LiteSpeed cache hit was found. A preload warning alone does not diagnose the backend outage.

Local deployment contains Windows-only frontend sharp binaries. Backend native dependencies are Linux binaries in a Windows workspace. Native dependencies cannot be transferred between these platforms. Backend previously loaded sharp while importing routes, so a bad binary could prevent startup. It now loads only when an image is processed.

## Changes

- One Express CORS middleware before parsers and routes; exact production origins; credentials and Vary: Origin; 600-second preflight cache.
- API responses explicitly no-store and X-LiteSpeed-Cache-Control: no-cache, including preflights and route errors.
- /api/live checks Node/Express without MySQL. /api/health remains database readiness.
- GET requests no longer send unnecessary Content-Type: application/json. Authenticated Bearer requests and JSON mutations still require preflight.
- Startup resolves its own app directory, logs runtime identity, handles listen errors, and exits on fatal exceptions so the supervisor can replace the worker.
- MySQL connect timeout is 10 seconds and pending connection queue is bounded. This is not a query timeout or a database outage fix.
- Homepage uses dynamic rendering and no-store fetches so outage fallbacks are not persisted by ISR. This trades page-cache performance for freshness; existing product/category pages were already dynamic.
- Next responses request no LiteSpeed page caching. Hashed asset browser caching remains intact.
- cPanel frontend packaging rejects non-Linux builds and stops explicitly copying local .env files. Public NEXT_PUBLIC_API_URL must be set at build time; server secrets belong in cPanel environment settings.

## cPanel recovery procedure

1. Back up the current release, environment settings, document-root .htaccess, and persistent uploads. Prepare a new release directory. Do not delete cPanel-managed node_modules symlinks, Passenger directives, or uploads.
2. Inspect the Node App Selector stderr/startup log and cPanel Errors immediately after restarting the backend. If no app log appears, ask the host for Passenger/LiteSpeed error logs and CloudLinux LVE faults at that time (memory, processes, CPU). Determine the actual failure before changing resource limits.
3. Use a supported Node 22 or 24 runtime for both apps. Installed Next requires at least Node 20.9.0. App roots must be separate; backend startup app.js; storefront startup server.js; application URLs must map to the intended domains at /. Keep cPanel-generated PassengerAppRoot, PassengerNodejs and PassengerStartupFile entries consistent with App Selector settings.
4. In the backend app's activated Node environment, install from its lockfile on Linux: npm ci --include=optional. If cPanel manages node_modules as a symlink, use the provider's supported dependency installation procedure rather than removing that symlink. Then npm run build and npm test. Check require('sharp') on Linux before testing uploads.
5. Set NODE_ENV=production, JWT_SECRET, MYSQL_HOST, MYSQL_USER, MYSQL_PASSWORD and MYSQL_DATABASE in the backend environment; verify MySQL user database privileges. Preserve R2/SMTP credentials as needed. Do not print credentials in logs. Do not force a TCP port or add manual Apache ProxyPass rules around App Selector: Passenger intercepts Node listen using its own socket.
6. Build the frontend on Linux with NEXT_PUBLIC_API_URL=https://admin.playbimboo.com/api using npm ci --include=optional and npm run build:cpanel. The packaging machine needs zip and unzip installed. Use the complete Linux-generated standalone folder: server.js, next-server.js, .next/server, .next/static, public and bundled dependencies. Do not mix files from different builds. Do not install over the finished standalone package unless the host requires a different supported deployment method.
7. Review and append the sibling .htaccess examples in each site's actual document root, preserving existing Passenger blocks. Do not inject wildcard credentialed CORS or duplicate Express CORS at Apache level. If the host overrides these cache rules, have it disable full-page caching for the API and Next HTML/RSC routes. Disable any HTML/CSS/JS rewriting optimizer for Next pages.
8. Switch to the complete new releases and restart both apps via App Selector. Purge existing LiteSpeed/CDN HTML and API cache once after switching. Retain old hashed static assets during the transition for already-open browser tabs, or use the host's release strategy to make them available. Never overwrite active .next files while workers are serving them.
9. Verify the acceptance checks below. Stop blaming CORS if /api/live still returns a LiteSpeed HTML 503: resolve hosting startup/mapping/resource errors first.

## Acceptance checks (run from an external terminal)

```sh
curl -i https://admin.playbimboo.com/api/live
curl -i https://admin.playbimboo.com/api/health
curl -i -X OPTIONS https://admin.playbimboo.com/api/categories \
  -H 'Origin: https://playbimboo.com' \
  -H 'Access-Control-Request-Method: GET' \
  -H 'Access-Control-Request-Headers: content-type,authorization'
curl -i https://admin.playbimboo.com/api/categories -H 'Origin: https://playbimboo.com'
curl -i https://admin.playbimboo.com/api/settings -H 'Origin: https://playbimboo.com'
curl -i 'https://admin.playbimboo.com/api/products?isVisible=true' -H 'Origin: https://www.playbimboo.com'
curl -I https://playbimboo.com/
```

Expected: live 200 JSON even with MySQL unavailable; health 200 when connected or 503 JSON when unavailable; allowed OPTIONS 204 with exact Access-Control-Allow-Origin, credentials true, allowed methods/headers, Vary: Origin and no-store. Public catalog routes must return JSON with the same origin and no-store. An untrusted Origin must receive no Access-Control-Allow-Origin. Validate authenticated login/logout, an admin mutation, a checkout, and an upload after recovery. Repeat homepage checks after a catalog update and ensure current data appears. Check actual rendered CSS links for 200 text/css; do not remove Next-managed preloads simply to silence a timing warning.
